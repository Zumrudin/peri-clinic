# План реализации: мобильная сетка аппаратов и полный каталог

Статус: реализовано в ветке `feat/equipment-mobile-grid`. Результаты и ограничения проверок: [QA-отчёт](../../qa/equipment-mobile/README.md). Ниже сохранён исходный план работ.

Спецификация: [equipment-mobile-grid-design](../specs/2026-09-12-equipment-mobile-grid-design.md).
Референс: https://dev.zumrudin.ru/peri-concepts/equipment-mobile-2026-09-12/01-grid-all-devices.png

## 1. Подтверждённое текущее состояние

- `src/components/home/Devices.astro`: мобильная карусель 82vw, карточки 510 px, изображения 355 px; breakpoint 800 px.
- `src/content.config.ts`: коллекция `devices` фильтрует published и show_on_home=true. Для полного каталога непригодна без отдельной выборки.
- `src/lib/homeContent.ts`: сортировка через bySort; href из procedure.slug, иначе общий /uslugi-i-ceny.
- `src/pages/[slug].astro`: страницы аппаратов фактически используют существующие процедуры и DevicePage. Новые URL для этих страниц не требуются.
- Отдельной страницы каталога нет в src/pages; среди CMS pages при проверке не найдено аппаратного каталога.
- CMS содержит 8 опубликованных аппаратов, 7 выбраны для главной. Ultraformer скрыт с главной, фото и procedure отсутствуют. Старый seed не отражает актуальное содержимое.
- Запись открывает контактный dialog, обработчик data-open-sheet уже используется на сайте.
- Рабочее дерево содержит пользовательские изменения CLAUDE.md и материалы editorial. Не включать их в изменения этой задачи и не откатывать.

## 2. Принятые решения

1. Мобильная главная показывает первые четыре опубликованных аппарата с show_on_home=true в порядке sort. Сейчас это Morpheus8, Volnewmer, InMode, ProFacial.
2. Десктоп продолжает показывать все выбранные аппараты, без общего slice(0,4) в getHomeContent.
3. Создать /apparaty для всех опубликованных записей. Перед созданием проверить отсутствие совпадающего slug среди categories/procedures/pages и redirect map.
4. Не включать Ultraformer на главную и не менять CMS-фотографии по предположению. Сверить актуальные медиа; старые локальные имена файлов ненадёжны.
5. Новые пользовательские подписи и SEO-тексты хранить в CMS. Путь /apparaty — фиксированное архитектурное решение, не произвольный URL редактора.
6. Предпочесть единую разметку карточек главной с мобильными стилями и скрытием элементов после четвёртого на мобильном. Не дублировать карусель целиком и не загружать две версии одинаковых изображений.

## 3. Этап A — данные CMS и миграция

Файлы: `directus/setup/collections.mjs`, `src/content.config.ts`, новый адресный скрипт миграции и JSON с согласованными подписями в `scripts/migrate/`.

- Добавить в singleton home поля: devices_all_label («Все аппараты»), devices_consultation_title («Поможем выбрать процедуру»), devices_consultation_label («Начать с консультации»), devices_catalog_title («Аппараты клиники»), devices_catalog_seo_title и devices_catalog_seo_description.
- Применить поля существующим идемпотентным механизмом схемы; проверить права build-роли и обновить snapshot, если это требуется действующим процессом репозитория.
- Подготовить dry-run/apply миграцию только новых полей, с backup до записи и без перезаписи непустых редакторских значений. Номер выбрать после проверки занятых номеров, 08-editorial уже существует.
- Не запускать общий seed-home для заполнения подписей: он содержит устаревший состав и изображения аппаратов.
- Добавить nullable/optional поля в home loader/schema и homeContent; при отсутствии подписи безопасно скрывать соответствующий новый элемент до миграции, не подменять содержимое молча.
- Добавить коллекцию allDevices с published-фильтром и limit=-1, независимо от show_on_home. Поля: id, sort, name, short, image.id/width/height, procedure.slug, procedure.status. Сохранить parseData и явную сортировку bySort.
- Обеспечить загрузку всего набора выбранных устройств для desktop; проверить limit текущего devices loader.

Выход этапа: полный каталог доступен из Astro Content Layer, существующая выборка главной не меняет смысл.

## 4. Этап B — слой данных каталога и корректные переходы

Файлы: новый `src/lib/deviceContent.ts`, `src/lib/homeContent.ts`, при необходимости `src/content.config.ts`.

- Реализовать getAllDevices через allDevices и bySort; шаблоны не обращаются к Directus напрямую.
- Сформировать модель: id, name, short, optional image, optional href. Формировать ссылку только для связанной опубликованной процедуры, чья страница действительно генерируется.
- Переиспользовать преобразование, где это не меняет существующее desktop-поведение; не перенаправлять отсутствующую страницу на фиктивный URL.
- На странице каталога запись без фото остаётся в списке. Для Ultraformer сейчас предусмотрена нейтральная область с названием и карточка без ссылки; общая консультация остаётся доступна.
- Если обнаружена ошибочная связь модели и процедуры, зафиксировать её в отчёте данных; исправлять только по подтверждённому соответствию, с резервной копией.

Выход этапа: каталог содержит все опубликованные записи и только рабочие детальные ссылки.

## 5. Этап C — мобильная сетка

Файлы: `src/components/home/Devices.astro`, `src/scripts/rail.ts` только при необходимости.

- Сохранить desktop CSS и набор карточек; перед изменениями снять baseline на 1024/1440 px.
- При max-width:800px заменить локальный equipment rail на grid repeat(2,minmax(0,1fr)); отменить overflow/scroll-snap/flex-basis/min-width/fixed height, относящиеся к карусели.
- Не переопределять глобальный класс .rail или .glass-panel для всего сайта. Использовать собственные классы компонента.
- Скрыть мобильное вступление, номера и управление каруселью, карточки после четвёртой. При менее четырёх записях показать доступные, без дублей и фиктивных карточек.
- Разделить изображение и текстовую область. Изображение contain, разумные мобильные sizes около половины контейнера, существующая Astro-оптимизация, lazy loading и заданные размеры против сдвигов разметки.
- Реализовать шахматные песочный/серо-зелёный фоны, 18–22 px радиус, читаемые названия и подписи. Стрелка aria-hidden, без вложенной кнопки в ссылке.
- Не задавать фиксированную общую высоту. На 320 px позволять описаниям расти и отводить стрелке отдельную строку.
- Убрать лишний tab-stop контейнера на мобильном; если rail.ts управляет tabindex, ограничить изменение только equipment rail и реагировать на смену media query. Проверить обратное переключение на desktop.
- Встроенный em заголовка сейчас может задавать золотой курсив: на мобильном привести его к спокойному начертанию референса локальным стилем, сохранив CMS-текст и desktop-вид.

Выход этапа: рабочая сетка 2×2 с актуальными данными, десктопная карусель сохранена.

## 6. Этап D — каталог /apparaty

Файлы: новый `src/pages/apparaty.astro`, `src/lib/deviceContent.ts`, `src/pages/sitemap.xml.ts`.

- Использовать существующий Page layout, CMS-заголовок и SEO-поля.
- Вывести весь опубликованный список, без фильтра главной и ограничения четырьмя элементами. На мобильном две колонки, на широком экране адаптивная сетка в контейнере сайта.
- Переиспользовать карточку через небольшой компонент, только если это действительно снижает дублирование и не меняет desktop-главную.
- Карточки без фото/ссылки обрабатывать по этапу B. Не скрывать опубликованный аппарат только из-за неполноты медиа.
- Добавить /apparaty в sitemap. Сохранить старые slug страниц процедур; проверить коллизии перед добавлением статической страницы.
- Обработать пустой каталог без поломанной сетки: оставить заголовок и доступную консультацию.

Выход этапа: кнопка главной имеет реальную целевую страницу с полным списком.

## 7. Этап E — кнопка и консультация

Файл: `src/components/home/Devices.astro`.

- После сетки добавить мобильную ссылку на /apparaty с CMS-подписью «Все аппараты», декоративной стрелкой, высотой от 48 px, золотистым контуром и полной шириной.
- Через 12–16 px добавить плашку с CMS-заголовком и button data-open-sheet; переиспользовать текущую аналитику контактной панели без создания дублей целей.
- Декоративную ветку не считать обязательным ресурсом; предпочтителен чистый светлый фон, пока нет подходящего ассета.
- Оба новых элемента показывать только на мобильной главной, сохраняя desktop-композицию.
- Учесть текущие отступы layout под MobileCtaBar и safe-area; не добавлять второй фиксированный бар.

## 8. Этап F — проверки и демонстрация

Среда: Node 22, существующая конфигурация Directus. Не выводить токены в логи или публикуемые артефакты.

Команды после реализации:

```bash
npm run check
npm test
npm run build
node scripts/qa/check-links.mjs
# После запуска npm run preview:
node scripts/qa/a11y.mjs http://127.0.0.1:4322 / /apparaty
node scripts/qa/screenshots.mjs http://127.0.0.1:4322 docs/qa/equipment-mobile / /apparaty
```

- Проверить доступность astro check в установленном окружении; отсутствие инструмента не выдавать за успешную проверку.
- Стандартный screenshot runner снимает только 375/800/1440. Добавить целевой QA runner для 320/390/430/801/1024 px или параметр ширин без изменения стандартного поведения.
- Проверить отсутствие горизонтального overflow, полную видимость текстов и фото, порядок четырёх карточек, корректное скрытие пятой и следующих на mobile, сохранение всех семи на desktop.
- У каталога проверить все восемь опубликованных записей; переходы по связям, Ultraformer без фото/ссылки, изменение ширины и отсутствие наложения нижней панели.
- Открытие/закрытие contact sheet, возврат фокуса, клавиатура, reduced motion, переход «Все аппараты» при выключенном JS.
- Проверить крайние состояния на временных данных без записи в production CMS: 0/1/3/5 выбранных устройств, длинные подписи, пустое фото, отсутствующая/черновая связанная процедура.
- Добавлять автоматические тесты только для содержательной логики фильтрации, сортировки и доступности ссылок, если она вынесена в чистую функцию; не писать тесты на значения CSS.
- После сборки убедиться, что HTML не содержит закрытых Directus URL с access_token.
- Финальные скриншоты разместить в отдельной папке /var/www/peri-concepts/equipment-mobile-implementation-<date>/, проверить HTTPS 200 и image/png и дать пользователю прямые ссылки.

## 9. Завершение и откат

- Отчёт: что изменено, состав карточек, адрес каталога, результаты проверок, оставшиеся несоответствия CMS-медиа.
- Реализацию показывать на preview до публикации. Текущая задача — подготовка плана; этот этап не выполняется сейчас.
- При дальнейшем выпуске использовать штатный deploy/rebuild процесс и предыдущий release для отката; новые nullable CMS-поля оставить совместимыми со старой сборкой.
- Не коммитить и не выкатывать посторонние изменения рабочего дерева вместе с этой задачей.
